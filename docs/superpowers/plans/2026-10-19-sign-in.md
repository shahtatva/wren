**Goal:** Real sign-in with Supabase email and password, routed through voice/, so a deployed voice server knows who is talking and refuses everyone else.

**Architecture:**
- **Routes.** voice/ gets four POST routes:
  - Two call Supabase Auth with the server's key: sign in with email and password, and refresh a session.
  - `/auth/age` records the 18+ confirmation for a signed-in user.
  - `/auth/signout` ends the user's Supabase session.
- **The browser** keeps the access token in memory and the refresh token in `localStorage`. It sends the access token in the WebSocket hello (`token`) and as `Authorization: Bearer` on `POST /turn`, `/auth/age` and `/auth/signout`.
- **Checking a token.**
  - voice/ asks Supabase (`GET /auth/v1/user`). The project has no asymmetric signing keys (its JWKS endpoint returned 404 on 2026-10-19), so local verification isn't available.
  - It caches the answer for at most 5 minutes, and never past the token's `exp`. Expired entries are evicted on every insert, so the cache stays small, and a revoked session stops working within 5 minutes.
  - A token Supabase refuses is remembered as refused for 60 s, keyed by its SHA-256, never the token itself.
  - Lookups are capped at 25 per 5 minutes overall, so junk tokens can't spend the shared Supabase budget. Supabase lists `/auth/v1/user` under a limit of 30 per 5 minutes per IP, and every lookup comes from voice/'s one IP. Over the cap, the hello is refused as `unavailable`, which is transient (4503).
- **Identity.**
  - A verified token becomes the user. The loopback dev identity stays for local work, and it skips the age check, because it only exists on the owner's machine.
  - Tokens are checked when a socket opens and on every `POST /turn`. An open socket keeps its identity until it closes, which is at most 45 minutes (the session cap). Signing out closes the page's socket and ends the Supabase session.
  - One exception: until Deepgram sends get a deadline (the live-path review's Important 2), a socket stuck in a stalled send can outlive the cap.
- **Age check.**
  - At hello and on `POST /turn`, a signed-in user needs `profiles.age_confirmed_at`.
  - The process remembers each confirmed user, since a confirmation never reverts.
  - If the database can't answer for a user it doesn't remember yet, the session is refused with `age_check_failed`. 18+ is a product rule, so the check fails closed.
- **Throttling.** Every Supabase Auth call comes from voice/'s one IP, so Supabase's per-IP limits are shared by everyone. voice/ limits sign-in attempts per email and across all emails, in memory, which also slows password guessing. That works because Render runs one instance.

**Tech Stack:** FastAPI and httpx (already used), Next.js 16 client components, pytest with `httpx.MockTransport`, `node --test`. No new dependencies.

**Spec:**
- `docs/superpowers/specs/2026-10-16-voice-loop-design.md`, "Keys and access". It says:
  - real sign-in comes before any deploy;
  - it's routed through voice/, because the browser never talks to Supabase;
  - the likely shape is Supabase email codes, with the hello carrying a JWT. This plan keeps the JWT in the hello but signs in with a password instead (see the revision note above).
- `CLAUDE.md`: the browser talks only to voice/; 18+ only; row-level security stays on; Wren discloses that it's an AI.

## Global Constraints

- The browser never calls Supabase, and no key reaches the browser: `python -m app.tools.leak_check` passes after `npm run build`. After the live-path fixes, it scans the whole web build.
- Invite-only: voice/ has no sign-up route, and the owner turns off "Allow new users to sign up" in the Supabase dashboard, so only accounts the owner creates can sign in.
- The password goes from the browser to voice/ to Supabase, over HTTPS once deployed. It's never stored, cached or logged, and the page keeps it only in the form field.
- 18+ only: no session starts until `profiles.age_confirmed_at` is set for the user. The dev identity is the only exception.
- User-facing copy follows the wren-voice skill: the sign-in screen, the age step, and errors including throttling. A wrong email and a wrong password get the same message, so the screen doesn't reveal who has an account. Keep it plain and short, with no charm on trust screens. Each error says what happened and what to do next.
- Row-level security stays on: live queries keep running as `authenticated` with the verified user's id.
- Tokens and passwords never appear in logs.
- Free tiers only; no new dependencies.
- **Supabase's limits** (Supabase docs, read 2026-10-24):
  - Password sign-in and token refresh share `/auth/v1/token`: 150 requests per 5 minutes per IP, with bursts up to 30.
  - `/auth/v1/user` is listed at 30 requests per 5 minutes per IP.
  - No email is sent, so the built-in sender's 2 emails an hour doesn't matter here.
  - `Sb-Forwarded-For` with a secret key would make Supabase count each user's own IP, once IP forwarding is enabled in the project's settings. Not needed at this scale.
  - **What throttling can't fix:** anyone who knows an invited email can lock that account's sign-in for 15 minutes, and anyone can lock everyone's for 5 minutes by spraying attempts. A CAPTCHA would narrow that. It's a new account, so it waits for the owner's decision.
- Don't hard-code test counts in steps, because the live-path fixes change them.

## Review Focus

1. **An expired access token at reconnect.** Sessions last at most 45 minutes, since the cap holds after the live-path fixes, and tokens last about 1 hour. The client must refresh before reconnecting, not bounce to sign-in (Task 4, `refreshes before reconnecting when the token is near expiry`, in `web/tests/client.test.ts` through the client harness).
2. **A wrong email or password.** The user gets plain copy and can retry. Nothing crashes, no token is issued, and an unknown email gets the same message as a wrong password (Task 2, `test_sign_in_with_a_wrong_password_returns_a_plain_error`, `test_an_unknown_email_gets_the_same_error`).
3. **A signed-in user without the age confirmation.** The hello is refused with `age_unconfirmed`, the page shows the age step, `/auth/age` records the confirmation, and the next hello starts a session. The user doesn't sign in again (Task 3, `test_hello_without_age_confirmation_is_refused`; Task 4, `an age_unconfirmed refusal shows the age step, and confirming retries`).
4. **The database down at the age check.** A user the process doesn't remember is refused with `age_check_failed` and plain copy, on the transient close code. The page keeps that message and retries with backoff, so the session starts once the database is back. A remembered user goes on, with memory off (Task 3, `test_an_unanswered_age_check_closes_with_the_retry_code` and `test_a_remembered_adult_starts_while_the_database_is_down`; Task 4, `a 4503 refusal keeps the server's message and retries`).
5. **Logs.** No token or password appears in captured logs from the auth routes, the password tool or a refused hello (Task 2, `test_passwords_and_tokens_never_reach_the_logs`; Task 3, `test_a_refused_hello_never_logs_its_token`). Bad client messages are already covered by the live-path fixes (Task 6).

**Interfaces:**
- Consumes: `SupabaseAuth` and `Tokens` from Task 1.
- Produces:
  - **In `voice/app/throttle.py`** (created in Task 1):
    - `class SlidingWindow(limit: int, window_s: float, clock: Callable[[], float] = time.monotonic)`, with `allow(key: str) -> bool`. A request counts against a window only when every window it's checked against lets it through, so a refused request doesn't use up budget.
    - `class Throttled(Exception)`
  - **Throttles inside `SupabaseAuth`.** Keys are emails lowercased and stripped. Over a limit, the method raises `Throttled`.
    - `sign_in`: per email, 5 per 15 minutes and 20 a day; across all emails, 30 per 5 minutes, well under the 150 that sign-in shares with token refresh.
  - **`python -m app.tools.set_password EMAIL`:** the owner's way to give an account a password, with no email. It reads the password twice with `getpass`, finds the user through the Auth admin API (`GET /auth/v1/admin/users`), and sets it with `PUT /auth/v1/admin/users/{id}`, using the secret key in `apikey`. It prints only whether it worked, never the password.
  - **`store.confirm_age(conn, user_id, at, tz) -> None`:**
    - Upserts `profiles`. A new row gets `age_confirmed_at = at` and `timezone = tz`.
    - An existing row keeps its time zone and its first confirmation (`coalesce`).
    - It sets the time zone because a new row's default is `'UTC'`, and the live path prefers the profile's zone over the browser's.
  - **`store.age_confirmed(conn, user_id) -> bool`:** False when there's no row.
  - **`MemoryProvider.confirm_age(user_id, at, tz) -> None` and `MemoryProvider.age_confirmed(user_id) -> bool`:**
    - They go through `PostgresMemory` and its `_run`, which gives one reconnect-and-retry.
    - They raise when the database can't answer.
    - True answers are remembered in a `set[UUID]`, and so is every confirmation.
  - **`FixedProvider(memory, *, adult: bool | Exception = True)`** in `voice_fakes.py`: answers `age_confirmed` with `adult`, raising it if it's an exception, and records `confirm_age` calls.
  - **`FakeAuth(users: dict[str, UUID])`:** stands in for `SupabaseAuth.user_for_token`. `make_runtime` gains `auth=None` and passes it to `Runtime`. Tests send a token with `voice_session(rt, token="good-token")`.
  - **Routes.** All four check `Origin` against `ALLOWED_ORIGINS`, like `POST /turn`. `main.py`'s CORS middleware already allows POST with `authorization`.
    - `POST /auth/signin` with `{email, password}` returns `{access_token, refresh_token, expires_in, age_confirmed}`. A wrong email or password returns 400 with plain copy and no tokens, the same for both. `Throttled`, or Supabase's own 429, returns 429 with plain copy.
    - `POST /auth/refresh` with `{refresh_token}` returns `{access_token, refresh_token, expires_in}`.
    - `POST /auth/age` with `{tz}` and a bearer token records the confirmation and returns 204. Without a valid token, it returns 401.
    - `POST /auth/signout` with a bearer token calls `sign_out`, drops the token from the cache and returns 204.
