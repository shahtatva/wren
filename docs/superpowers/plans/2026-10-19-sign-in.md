# Sign-In Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Real sign-in with Supabase email codes, routed through voice/, so a deployed voice server knows who is talking and refuses everyone else.

**Architecture:**
- **Routes.** voice/ gets three POST routes that call Supabase Auth with the server's key: request a 6-digit code, verify it, and refresh a session.
- **The browser** keeps the access token in memory and the refresh token in `localStorage`. It sends the access token in the WebSocket hello (`token`) and as `Authorization: Bearer` on `POST /turn`.
- **Checking a token.** voice/ asks Supabase (`GET /auth/v1/user`) and caches the answer until the token's `exp`. The project has no asymmetric signing keys (its JWKS endpoint returned 404 on 2026-10-19), so local verification isn't available.
- **Identity.** A verified token becomes the user id. The loopback dev identity stays for local work.
- **Age check.** The first sign-in records the 18+ confirmation in `profiles.age_confirmed_at`.

**Tech Stack:** FastAPI and httpx (already used), Next.js 16 client components, pytest with `httpx.MockTransport`, `node --test`. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-10-16-voice-loop-design.md`, "Keys and access". It says: real sign-in before any deploy, routed through voice/ because the browser never talks to Supabase; the likely shape is Supabase email codes, with the hello carrying a JWT.

Also `CLAUDE.md`: the browser talks only to voice/; 18+ only; row-level security stays on; Wren discloses it is an AI.

## Global Constraints

- The browser never calls Supabase, and no key reaches the browser: `python -m app.tools.leak_check` passes after `npm run build`.
- Invite-only to start: code requests send `create_user: false`, so only accounts created in the Supabase dashboard can sign in.
- 18+ only: no session starts until `profiles.age_confirmed_at` is set for the user.
- User-facing copy (sign-in screen, errors, age check) follows the wren-voice skill: plain, short, no charm on trust screens.
- Row-level security stays on: live queries keep running as `authenticated` with the verified user's id.
- Tokens and codes never appear in logs.
- Free tiers only; no new dependencies.

**Before Task 2's live check (you, in the Supabase dashboard):** Authentication → Email Templates → Magic Link: include `{{ .Token }}`, so the email carries the 6-digit code. Codes expire after 1 hour, and a user can request one every 60 seconds (Supabase defaults).

## Review Focus

1. **An expired access token at reconnect:** sessions last up to 45 minutes and tokens about 1 hour. The client must refresh before reconnecting, not bounce to sign-in (Task 4, `refreshes before reconnecting when the token is near expiry`).
2. **A wrong or expired code:** the user gets plain copy and can retry. Nothing crashes, and no token is issued (Task 2, `test_verify_with_a_bad_code_returns_a_plain_error`).
3. **A signed-in user without the age confirmation:** the hello is refused with code `age_unconfirmed` and the page shows the age step (Task 3, `test_hello_without_age_confirmation_is_refused`).
4. **Logs:** a token or code passed through any route must not appear in captured logs (Task 2, `test_codes_and_tokens_never_reach_the_logs`).
5. **A token plus a loopback address:** the token decides, and the dev identity is never used when a token is present (Task 1, `test_a_token_beats_the_dev_identity`).

- Test: `voice/tests/test_auth.py`, `voice/tests/test_identity.py`

**Interfaces:**
- Produces:
  - `class SupabaseAuth(url: str, key: str, client: httpx.AsyncClient | None = None)` with these methods:
    - `async user_for_token(token: str) -> UUID | None`: `GET {url}/auth/v1/user` with `apikey` and `Authorization: Bearer`. Returns `None` on 401. Caches by token until the token's `exp` (read the unverified payload for `exp` only).
    - `async send_code(email: str) -> None`
    - `async verify_code(email: str, code: str) -> Tokens`
    - `async refresh(refresh_token: str) -> Tokens`
  - `Tokens(access_token: str, refresh_token: str, expires_in: int)`
  - `async resolve_identity(token: str | None, client_host: str | None, dev_user_id: UUID | None, auth: SupabaseAuth) -> UUID | None`: a token decides when present; otherwise the dev identity, from loopback only.
- `Runtime` gains `auth: SupabaseAuth`.
